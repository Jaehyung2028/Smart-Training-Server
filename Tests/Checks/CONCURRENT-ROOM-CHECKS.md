# 멀티 접속 동시 요청 안정성 점검

## 결과
서버 전체 검사 469개를 통과했습니다. 아래 네 상황을 각각 40회, 총 160회 반복했으며 정원 초과·참가자 중복·잘못된 방장·진행 상태 불일치는 발견되지 않았습니다.

이번 변경은 검증 코드 추가입니다. 운영 서버와 Unity의 기능 코드는 변경하지 않았습니다.

## 추가한 검사
`Tests/Checks/ConcurrentRoomChecks.cs`의 `Run()`을 기존 검사 실행 목록에 추가했습니다.

- 마지막 한 자리: 방장 1명 접속 상태에서 12명의 예약 요청을 같은 시작 신호로 실행합니다. 한 명만 예약에 성공하며 실제 접속 확정 후에도 정원을 지켜야 합니다.
- 방장 퇴장과 입장 확정: 기존 참가자와 입장 예약자가 있는 방에서 방장 퇴장과 새 참가자의 접속 확정을 겹쳐 실행합니다. 남은 참가자 중 유효한 방장이 있어야 합니다.
- 시작과 새 예약: 방장 시작 요청과 새 입장 예약을 겹쳐 실행합니다. 먼저 처리된 요청에 따라 하나만 성공하고 진행 상태와 버전이 일치해야 합니다.
- 재접속과 이전 연결의 종료 알림: 재접속용 새 토큰의 확정과 이전 토큰의 종료 알림을 겹쳐 실행합니다. 이전 알림이 새 참가자 정보를 삭제하지 않아야 하며 같은 확정 요청을 재전송해도 중복 참가자가 생기지 않아야 합니다.

매번 예약 수와 사용자 PendingRoomId, 참가자 CurrentRoomId, 참가자 슬롯 중복, 정원, 방장 소속을 함께 검사합니다.

## 관련 서버 함수
- `RoomService.JoinRoom()`: 예약 및 정원 확인
- `RoomService.ConfirmConnection()`: 실제 연결 확정 및 중복 확인
- `RoomService.ClientDisconnected()`: 현재 토큰과 일치하는 연결만 정리
- `RoomService.LeaveRoom()` / `ChangeMaster()`: 퇴장 및 방장 자동 위임
- `RoomService.SetRoomPhase()`: 입장 예약과 진행 상태 변경의 충돌 방지

## 검증 범위
새 검사는 서버 서비스를 병렬 호출하는 자동 검사입니다. 12개의 Unity 실행 파일을 별도 PC에서 띄운 네트워크 부하 시험을 의미하지 않습니다. 기존 API 검사도 함께 실행했습니다.

## 실행 및 직접 확인
서버 저장소 루트에서 `dotnet run --project Tests/Checks/Checks.csproj`로 실행합니다. 검사 프로젝트는 .NET 10 SDK를 사용합니다.

직접 확인할 때는 Unity 클라이언트를 여러 개 실행하여 아래 동작을 확인합니다.
1. 최대 인원 2명인 방에 방장을 접속시킨 뒤 다른 두 클라이언트에서 동시에 참가합니다. 한 명만 들어가고 나머지에는 정원 안내가 표시되어야 합니다.
2. 방장이 퇴장하는 동안 다른 클라이언트가 참가합니다. 남아 있는 참가자에게 방장이 표시되어야 합니다.
3. 모두 준비된 방에서 방장 시작과 다른 사용자의 참가를 동시에 누릅니다. 진행 중 방에 새 참가자가 들어가서는 안 됩니다. 예약이 먼저 생기면 접속 완료 후 다시 시작해야 합니다.
4. 연결이 끊긴 클라이언트를 재접속합니다. 참가자 목록에 같은 사용자가 한 명만 표시되어야 합니다.
